# Lu Lu Sticker Tools v3 — 優化方向與執行計畫

> 建立日期：2026-11-25
> 依據：程式碼檢視（commit `da4fcc6`）＋ 2026 年 LINE 貼圖市場資料

---

## 1. 現況摘要

**已經做得不錯的部分**

- 全部在瀏覽器端完成，API Key 存在 localStorage 並有到期機制。
- 有完整流程：產生整張貼圖 → 用 Valley Finding 切片 → 合規檢查 → 編輯文字 → 模擬聊天室預覽 → 打包 ZIP。
- 內建 13 種氛圍預設，每種 24 組台詞（`services/geminiService.ts`），其中已有脆式熱梗、精神登出、牽牽、陰陽怪氣等趨勢題材。
- `tsc --noEmit` 和 `eslint` 都沒有錯誤。

**目前的缺口**

- 沒有任何測試，CI 只負責部署。
- 重新整理頁面後，產出的結果全部消失（沒有存檔）。
- 單一角色無法延續成「系列」：每次生成都從頭開始。
- 只支援 8、16、24 張，也只支援靜態貼圖。

## 3. 已確認的問題（P0：會導致上架被退件）

1. **單張重新生成的圖超過尺寸上限**
   - 位置：`App.tsx` 的 `handleRegenerateSlice`
   - `generateSingleSticker` 回傳約 1024×1024 的 1:1 圖。這張圖只經過去背和 `autoFixMargin`。
   - `autoFixMargin` 會沿用原圖尺寸，沒有縮到 370×320 以內，所以 ZIP 裡會出現超大的圖。

2. **手動上傳替換的圖變成白底 JPEG**
   - 位置：`ResultsView.tsx:118`
   - 這裡呼叫的 `processFileToBase64` 原本是為 Gemini 參考圖設計的：會填白底、轉成 JPEG、最大 1536px。
   - 結果是 ZIP 裡出現 `.png` 檔名的 JPEG，沒有透明背景，尺寸也超標。

3. **合規檢查漏了兩項**
   - `validateSticker` 沒有檢查最大尺寸 370×320，也沒有檢查 1MB 檔案大小。
   - `ValidationIssue` 型別裡宣告了 `'filesize'`，但從未使用。
   - 所以上面兩個問題會顯示為「通過」。

**其他較小的問題**

- `public/` 資料夾不存在，但 `vite.config.ts` 的 PWA manifest 引用了 `pwa-192x192.png`、`favicon.ico` 等圖示，這些檔案都會 404。
- README 和 MANUAL 寫的模型是「Gemini 1.5 Pro」，但程式實際用的是 `gemini-3-pro-image-preview`。另外 `ModelOption` 有兩個值對應到同一個模型。
- 錯誤處理用的是 `alert()`。遇到 429（配額用完）也沒有友善提示或重試。
- 部分 UI 描述直接寫了現有角色 IP 的名稱（例如「吉伊卡哇式」）。LINE 審核禁止模仿既有角色，建議改成中性描述，並確認提示詞沒有帶入 IP 名稱。

## 4. 優化方向

1. **合規零退件**：所有輸出都只經過同一個規格關卡，並用測試保護。
2. **角色續航**：建立角色庫，同一角色可以穩定地產出第 2、3……組。這是市場上最關鍵的成功因素。
3. **趨勢內容引擎**：把台詞和氛圍資料從程式碼抽出來，可以按季更新；並支援無字模式和多語系。
4. **新格式**：32 和 40 張、主圖與標籤圖專屬生成、動態貼圖（APNG）、表情貼。
5. **上架一條龍**：自動產生標題、說明、標籤（中、日、英），並提供 AI 使用聲明檢查清單。

## 5. 執行計畫

### Phase 0：合規修補與基礎建設（約 1 週）

| # | 任務 | 主要檔案 | 完成標準 |
|---|---|---|---|
| 0.1 | 新增 `enforceLineSpec(img)` 作為唯一的輸出關卡：縮到 ≤370×320、寬高為偶數、10px 邊距、PNG、≤1MB | `utils/imageProcessor.ts` | 切片、重新生成、上傳替換、編輯器輸出、ZIP 打包都走這個函式 |
| 0.2 | 上傳替換改用新的 `loadStickerFile()`，保留透明背景、輸出 PNG。`processFileToBase64` 只留給參考圖使用 | `ResultsView.tsx`、`imageProcessor.ts` | 上傳透明 PNG 後，ZIP 裡仍是透明背景 |
| 0.3 | `validateSticker` 加上最大尺寸與檔案大小檢查 | `imageProcessor.ts` | 1024×1024 的圖會顯示 error |
| 0.4 | 導入 Vitest。把 Valley Finding 的密度計算、切割點搜尋、邊界計算抽成純函式（輸入 `Uint8ClampedArray`） | `utils/`、`package.json` | 8、16、24 格的合成測試圖都能切出正確格數 |
| 0.5 | CI 加入 `lint`、`tsc`、`test`、`build` | `.github/workflows/` | PR 會自動跑這四項檢查 |
| 0.6 | 補上 `public/` 的 PWA 圖示；文件裡的模型名稱與程式同步；合併重複的 `ModelOption` | `public/`、`README.md`、`MANUAL.md`、`types.ts` | build 後沒有 404 |

### Phase 1：角色續航與作品保存（約 2–3 週）

| # | 任務 | 說明 |
|---|---|---|
| 1.1 | **角色設定圖（Character Sheet）** | 先生成正面、側面和 3 種表情的設定圖，使用者確認後鎖定。之後所有整張生成和單張重生成都帶入這張圖當參考，提高角色一致性 |
| 1.2 | **角色庫（IndexedDB）** | 保存角色 DNA：描述、風格、字型、設定圖。下次可以直接「用這個角色再做一組」 |
| 1.3 | **專案自動保存** | 原圖、切片、編輯狀態都存進 IndexedDB，重新整理後可以還原；並提供歷史紀錄列表 |
| 1.4 | **錯誤處理** | 依 429、403、安全過濾分類顯示訊息，429 用指數退避重試；用 Toast 取代 `alert()` |
| 1.5 | **重新生成時避開重複** | 單張重生成時，把同組其他格的動作描述放進提示詞並要求避開，降低重複 |

### Phase 2：趨勢內容引擎與更多張數（約 3–4 週）

| # | 任務 | 說明 |
|---|---|---|
| 2.1 | **把台詞資料抽成檔案** | 把 `geminiService.ts` 裡約 300 行的台詞資料移到 `data/vibes/*.json`，加上 `updatedAt` 和 `tags` 欄位。這樣按季更新題材時不用改程式 |
| 2.2 | **新增趨勢包** | 死語復興（LKK、瞎趴、哇哩咧）、反差組合、節慶包（農曆新年、情人節、中秋、聖誕）。每季檢查一次熱梗 |
| 2.3 | **無字模式＋多語系輸出** | AI 只畫圖、不寫字，文字改由 Canvas 疊加。這樣同一組圖可以輸出中文、日文、英文版本，對應創作者「少用文字、跨市場」的建議，也解決 AI 寫錯字的問題 |
| 2.4 | **32 和 40 張** | 拆成 2–3 張 16 格分批生成，共用角色設定圖，再合併成一組並重新編號 |
| 2.5 | **主圖與標籤圖專屬生成** | 現在是把某張貼圖縮小成 96×74，在聊天室裡幾乎看不清楚。改成單獨生成「角色大頭」版本 |
| 2.6 | **一組貼圖的情緒覆蓋檢查** | 檢查這組是否涵蓋打招呼、感謝、OK、道歉、晚安等高頻需求，缺少時提示使用者 |

### Phase 3：新格式與上架輔助（約 4–6 週）

| # | 任務 | 說明 |
|---|---|---|
| 3.1 | **動態貼圖（APNG）** | 先做「程式產生的動態」：彈跳、搖晃、放大、閃爍，套在靜態貼圖上，用 `upng-js` 編碼。成本低又好控制；之後再考慮 AI 生成關鍵影格。規格（最大 320×270、5–20 影格、≤4 秒、≤300KB）實作前要再對照官方指南 |
| 3.2 | **表情貼（Emoji）** | 180×180，8–40 個。**動工前先確認 LINE 對 AI 表情貼的規範**，因為大賽不開放 AI 表情貼 |
| 3.3 | **上架資料產生器** | 用 Gemini 文字模型產生中、日、英的標題、說明和建議標籤，並附上 AI 使用聲明與原創性檢查清單 |
| 3.4 | **隨你填（Custom）貼圖** | 先研究官方規格，再評估是否投入 |

### 暫緩項目

- **後端與 LoRA 訓練**：與「完全在客戶端、不經過伺服器」的隱私承諾衝突。先用角色設定圖加參考圖的方式處理一致性。
- **Telegram、Discord 輸出**：等 LINE 的主流程穩定之後再做（技術上只是另一組尺寸設定）。

## 7. 建議的第一步

先做 Phase 0 的 0.1–0.3。三個 P0 問題都集中在 `imageProcessor.ts`，改動範圍小，又直接影響使用者能不能順利上架。接著做 0.4 的測試，替後面的重構打底。
